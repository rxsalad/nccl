# 多机实验（主机内存版）：经 RDMA（RoCE）在两台机器之间读写 CPU 内存

两台机器（server-0、server-1）上各跑一个纯 C 程序，让 server-0 经 **RDMA（RoCE v2）** 直接读写 server-1 的**普通进程内存**：

- `server-cpu.c`：运行在 server-1，**被动方**——准备内存、注册给网卡、告诉对端地址与 rkey，之后只负责校验；
- `client-cpu.c`：运行在 server-0，**主动方**——连接、建 QP、发起 RDMA WRITE / READ、校验、测带宽；
- **OOB（带外）通道**：两端经 `eth0` 上的 TCP，**只交换控制信息**；
- **数据通道**：RoCE v2 的 RDMA，网卡直接读写对端内存，对端 CPU 不参与。

两个程序都是**纯 C**，只依赖 `libibverbs`。

**状态**：定稿（2026-11-01 重写；实验数据均于 2026-10-31 在 server-0 / server-1 上测得）。文中所有"实测"都按当前源码得到，每个结论的可靠程度见附录 A，已知局限见附录 B。

> **关于流量类别（traffic class）**：本集群上，运行 NCCL 必须设置 `NCCL_IB_TC=104`。本篇的裸 verbs 程序对应的开关是 `-t`（**两端都要设**）。实测表明它对主机内存的 RDMA READ 影响巨大（§5.4），所以文中推荐配置一律是 **`-t 104`**，同时给出默认 `-t 0` 的数据作对照。交换机队列配置的通用背景见 [roce-swtich.md](roce-swtich.md)。

## 1. 全貌

[↑ 返回目录](#toc)

<a id="1-1"></a>
### 1.1 做什么、怎么做

| 项 | 做法 |
|---|---|
| 语言与依赖 | 纯 C；`gcc`；只依赖 `libibverbs` |
| 内存来源 | `posix_memalign`（4096 字节对齐） |
| 填充与校验 | CPU 循环填充；校验**直接读主机内存**比较，不需要拷贝 |
| 注册给网卡 | `ibv_reg_mr(主机指针)`，走内核标准钉页路径，不需要额外内核模块 |
| 注册前的准备 | 先把每一页写一遍（见 §3.3） |
| OOB | `eth0` 上的 TCP，只交换控制信息 |
| QP | RC（可靠连接），手工 `ibv_modify_qp` 建连 |
| 默认网卡 / 端口 / 区域大小 | `mlx5_0`（client）、`mlx5_14`（server）；5555；64 MiB |

**时间线**：

```
  server-1（被动方）                               server-0（主动方）
  ① 准备主机内存、ibv_reg_mr、建 QP → INIT          ① 准备主机内存、ibv_reg_mr、建 QP → INIT
  ② eth0 上 listen、accept          ◄──── TCP connect ────  ② 连接 server 的 eth0 地址
  ③ 交换 conn_info（QP 号、GID、addr、rkey ...）  ◄───────►  ③ 同左
  ④ QP → RTR → RTS                                  ④ QP → RTR → RTS
  ⑤ 等待命令                                        ⑤ RDMA WRITE → 经 OOB 发 'W' → server 校验、回 'K'
                                                    ⑥ RDMA READ → 本端校验
                                                    ⑦ 带宽：连续 WRITE / READ；发 'B' 再校验；发 'Q' 结束
```

**两条通道别混**：OOB（`eth0`）只传"QP 号、GID、地址、rkey"和"写完了 / 校验结果"这类控制信息；数据走 RDMA，两端网卡直接在两块内存之间搬运，不经过 `eth0`，也不经过内核网络栈（证据见 §5.5）。

<a id="1-2"></a>
### 1.2 环境

- 两个 Pod 分别在两个不同的 GPU 节点上（StatefulSet `server` 的 `server-0`、`server-1`）；
- client 用 `mlx5_0`、server 用 `mlx5_14`；RoCE v2、400 Gb/s（4X NDR）、`active_mtu = 4096`；
- 两个 Pod 里**只有偶数号网卡可用**（`mlx5_0/2/…/14`；`/dev/infiniband` 下只有偶数号的 `uverbs`）；
- OOB 走 `eth0`，server 在 `eth0` 的 `10.133.0.253` 上监听；
- 本篇**没有**研究主机内存与网卡之间的 NUMA 亲和性（未测）。

**推荐配置**：`-t 104`（两端都设）。理由见 §5.4。

## 2. 原理：建立连接并读写对端内存

[↑ 返回目录](#toc)

<a id="2-1"></a>
### 2.1 对象

| 术语 | 含义 | 本程序里 |
|---|---|---|
| **PD**（保护域） | QP、MR 必须属于同一个 PD 才能配合使用 | 每端一个 |
| **MR**（内存区域） | 注册给网卡的一块内存，注册后得到 `lkey`（本端用）与 `rkey`（给对端用） | 每端一个，整块 128 MiB |
| **QP**（队列对） | 通信的端点，一对 QP 构成一条连接；本程序用 **RC**（可靠连接），支持单边读写 | 每端一个 |
| **CQ**（完成队列） | 本端发起的操作做完后，网卡在这里放一条完成项 | 每端一个，深度 256 |
| **WR / WC**（工作请求 / 完成项） | 向 QP 提交的一个操作 / CQ 里的一条完成记录 | `post_op` / `wait_cq` |
| **lkey / rkey** | MR 的本地 / 远端访问凭证 | `lkey` 用在本端 `sge.lkey`；`rkey` 经 OOB 告诉对端 |
| **GID** | RoCE 用来寻址的"地址"，形如 IPv6 地址 | 自动选 `gid[3]`（fabric 的 ULA 地址；`gid[1]` 是 fe80 链路本地，不能跨机路由） |
| **OOB** | Out-Of-Band，带外：这里指 `eth0` 上的 TCP | §2.2 |

<a id="2-2"></a>
### 2.2 OOB 交换了什么

OOB 通道只传**控制信息**，分两类：一次性的**连接信息**，和后面零星的 **1 字节同步命令**。

**① 连接信息：两端各发一份 `struct conn_info`，只交换一次**

```c
struct conn_info {
  uint32_t qpn;        // QP 号
  uint32_t psn;        // 起始包序号
  union ibv_gid gid;   // 16 字节，RoCE 的"地址"
  uint64_t addr;       // 已注册内存的起始虚拟地址
  uint32_t rkey;       // 远端访问凭证
  uint64_t len;        // 已注册的字节数
};
```

结构体大小 **48 字节**（偏移：`qpn`@0、`psn`@4、`gid`@8、`addr`@24、`rkey`@32、`len`@40，`rkey` 之后有 4 字节对齐填充），由同样的定义在 Pod 里编译后用 `sizeof` / `offsetof` **实测**得到。

| 字段 | 对端拿它做什么 |
|---|---|
| `qpn` | QP 切到 RTR 时的 `dest_qp_num`：告诉网卡"包要送给对端的哪个 QP" |
| `psn` | 对应 RTR 的 `rq_psn`，必须与对端发送的起始序号一致，否则包会被当成乱序 |
| `gid` | RTR 的 `ah_attr.grh.dgid`：RoCE 靠它路由到对端网卡 |
| `addr` | 之后每次 RDMA 操作的**远端地址**（`remote_addr`） |
| `rkey` | 之后每次 RDMA 操作必须带的**远端凭证** |
| `len` | 只用来检查两端的 `-s` 是否一致，不一致就退出 |

交换顺序是 client **先发后收**、server **先收后发**，两边正好对上；如果两端都先收，就会互相等待（死锁）。结构体直接按原始字节收发，没有做字节序转换，前提是两端都是 x86。

**② 同步命令：1 字节，client → server**

| 命令 | 含义 | server 回复 |
|---|---|---|
| `'W'` | RDMA WRITE 做完了，请校验 `[0, n)` | `'K'`（正确）或 `'X'`（有不匹配） |
| `'B'` | 带宽测试做完了，请再校验一次 | 同上 |
| `'Q'` | 全部结束 | 无 |

**不通过 OOB 交换的**：数据（走 RDMA）；READ 的完成通知（READ 由 client 发起，它自己从完成队列知道做完了）；`lkey`（只在本端使用）。

**为什么必须有这个通道**：RDMA 的单边操作要求发起方事先知道对端的 QP 号、GID、内存地址和 rkey，这些信息只能先通过别的通道交换；`eth0` 上的 TCP 现成又可靠。

**与实测的对应**：§5.5 里 `eth0` 在一次运行中只多了约 0.001–0.002 MiB（1–2 KiB）。两个 48 字节的结构体、几条 1 字节命令加上 TCP 头，量级对得上（只是量级吻合，没有逐包核对）。

<a id="2-3"></a>
### 2.3 什么算"连接"

交换完信息、各自准备好之后，常说的"连接建立了"指的是：

> **连接 = 两端的 QP 互相配置好对方的地址信息（QP 号、GID、包序号），并切到 RTS；内存授权（`addr` + `rkey`）是另一层，每次操作时才用。**

| 信息 | 属于"连接"吗 | 用在哪里 |
|---|---|---|
| `qpn`、`psn`、`gid` | **是** | `ib_connect` 里 `ibv_modify_qp` 切到 RTR / RTS：包送给对端哪个 QP、路由到哪块网卡、序号对上 |
| `addr`、`rkey` | **否**（内存授权） | 每次 `post_op` 的 `remote_addr` 与 `rkey`：读写对端哪块内存、凭什么权限。它们只是随同一轮 OOB 顺便交换；同一个连接上可以换别的 MR 和 rkey |
| `lkey` | 否，且**不交换** | 只在本端用，`post_op` 的 `sge.lkey` |
| `len` | 否 | 只用来检查两端 `-s` 一致 |

两点容易混淆：

- **"连接"是每端本地 QP 里存的状态**。`ib_connect` 只是各自把对端信息填进自己的 QP，没有哪个函数是"去连对方"；
- **`eth0` 上的 TCP 连接不是 RDMA 连接**。TCP 只是临时的信令通道，交换完信息就完成了使命；RDMA 连接是 fabric 上两个 QP 之间的关系。本程序为了后面的 `'W'/'B'/'Q'` 同步才让 TCP 一直开着。

**可靠度**：QP 状态与 `ib_connect` 的做法是**代码事实**。"手工 `modify_qp` 建连时，连接阶段不在 fabric 上发握手包；信息填错要到第一次 WRITE / READ 才以重试耗尽之类的错误暴露"是 RC 手工建连的机制说法，**推断**：本篇没有抓包，也没有故意填错信息看现象；对比的 `rdma_cm` 建连（有专门的连接管理报文）本篇没有用。"中途关掉 TCP 是否影响已建立的 RDMA 传输"**未测**。

<a id="2-4"></a>
### 2.4 QP 状态机

QP 在建连时要依次经过三个状态；前一步在 `ib_setup`，后两步在 `ib_connect`（需要对端信息，所以要等 OOB 交换完）：

| 步骤 | 切换 | 需要的信息 | 关键参数 |
|---|---|---|---|
| ① | RESET → **INIT** | 无 | `pkey_index = 0`、`port_num = 1`、`qp_access_flags = REMOTE_READ \| REMOTE_WRITE`（**允许对端对本 QP 做远端读写**，不开则对端的 RDMA 读写会被拒绝） |
| ② | INIT → **RTR**（准备接收） | **对端**的 QP 号、PSN、GID | `dest_qp_num`、`rq_psn`、`path_mtu`（取网卡的 `active_mtu` = 4096）、`ah_attr`（`is_global = 1`、`dgid`、`sgid_index`、`hop_limit = 64`、`traffic_class`）、`max_dest_rd_atomic = 16` |
| ③ | RTR → **RTS**（准备发送） | 本端的 PSN | `sq_psn`、`timeout = 14`（等 ACK 超时 = 4.096 µs × 2¹⁴ ≈ 67 ms）、`retry_cnt = 7`（超时后最多重传 7 次，再失败报 `IBV_WC_RETRY_EXC_ERR`）、`rnr_retry = 7`（7 表示对端 RNR 时无限重试）、`max_rd_atomic = 16`（同时在飞的 RDMA READ 上限） |

RoCE 的两点特别之处：`is_global = 1`（必须带 GRH，用 GID 寻址，没有 InfiniBand 的 LID）；`hop_limit = 64`（两端 fabric 在不同子网，要经三层转发）。

<a id="2-5"></a>
### 2.5 单边操作：WRITE 与 READ

| 操作 | 方向 | 对端要做什么 |
|---|---|---|
| **RDMA WRITE** | 本端内存 → 对端内存 | **不做任何事**；对端的 CPU 不参与，也不知道数据已经到了 |
| **RDMA READ** | 对端内存 → 本端内存 | **不做任何事**；数据由对端网卡直接读出并发回 |

- 发起方每次操作都要给出 `(本地地址, 远端地址, rkey, 长度)`；`rkey` 必须是**对端**那块 MR 的；
- 对端注册 MR 时必须允许相应的远端访问（`REMOTE_WRITE` / `REMOTE_READ`）；本端要接收 READ 的数据，MR 还需要 `LOCAL_WRITE`；
- 对 RC 的 WRITE，完成项出现表示数据已被对端网卡确认收到（可靠连接的 ACK，RC 的标准语义，公开资料）；
- **WRITE 对对端是"无声"的**，所以要经 OOB 发 `'W'` 通知它去校验（§2.2）；
- `sge.length` 是 32 位，单次最多 4 GiB（本实验 64 MiB，远小于此）。

<a id="2-6"></a>
### 2.6 流量类别 `-t`

`-t` 经三步生效，最后落在 `ib_connect` 里 QP 从 INIT 切到 RTR 的那一步：

```c
/* ① main：解析命令行 */
case 't': tc = atoi(optarg); break;               // 默认 0

/* ② main：OOB 交换完连接信息之后，把 tc 传下去 */
ib_connect(&ib, &theirs, tc);

/* ③ ib_connect：RTR 阶段，写进地址向量里的 GRH 字段 */
a.qp_state = IBV_QPS_RTR;
a.ah_attr.is_global = 1;                          // RoCE 必须带 GRH
a.ah_attr.grh.dgid = r->gid;
a.ah_attr.grh.sgid_index = ib->gid_idx;
a.ah_attr.grh.hop_limit = 64;
a.ah_attr.grh.traffic_class = (uint8_t)tc;        // ← -t 的值在这里生效
```

`traffic_class` 是 GRH（全局路由头）里的字段，即 IP 头的 Traffic Class 字节：**高 6 位是 DSCP，低 2 位是 ECN**，即 `traffic_class = DSCP × 4 + ECN`。所以 `-t 104` = 0x68，DSCP = 26，ECN 位为 0；交换机据此把报文放进不同的队列。

| 要点 | 说明 |
|---|---|
| **每端各自设置，只管自己发出的包** | 值写在**本端 QP** 的地址向量里：client 的 `-t` 管 client 发出的包，server 的 `-t` 管 server 发出的包 |
| **READ 要两端都设** | READ 的数据是 server 发给 client 的（READ 响应），带的是 **server 端 QP** 的 traffic class。只在 client 设 `-t 104`，READ 数据仍按 TC 0 走——这是"两端都要设"的原因 |
| **只能在 RTR 转换时给** | `ibv_create_qp` 没有这个参数，只能通过 `ah_attr` 在 INIT → RTR 时设置 |
| **NCCL 的对应变量** | `NCCL_IB_TC=104`，设到的是同一个字段 |

**可靠度**：代码位置与字段含义来自本篇源码与 ibverbs 的字段定义，是**代码事实**；"104 对应 DSCP 26"是按字段定义换算的，**没有抓包验证**报文头里的 DSCP；"READ 要两端都设"是按 RoCE 机制**推断**的，本篇实测的是"两端同设 `-t 104`"的效果（§5.4），**没有单独测过只设一端**。交换机一侧如何处理这个 DSCP，见 [roce-swtich.md](roce-swtich.md)。

<a id="3"></a>
## 3. 注册主机内存

[↑ 返回目录](#toc)

<a id="3-1"></a>
### 3.1 做法

注册主机内存是 RDMA 注册的"标准情形"：内核钉住这些页，把各页的总线地址写进网卡的翻译表（MTT），并返回 `lkey` / `rkey`。本程序的做法：

```c
unsigned* buf;
posix_memalign((void**)&buf, 4096, total);             // 主机内存
fill_pattern(buf, n, 3u, 1u);                          // 先把每一页都写一遍（本程序里填数据时自然完成）
memset(buf + n, 0, region);
struct ibv_mr* mr = ibv_reg_mr(pd, buf, total,
        IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_WRITE | IBV_ACCESS_REMOTE_READ);
```

<a id="3-2"></a>
### 3.2 为什么要钉页、"按页"是什么意思

**为什么要锁住（钉页）**。网卡做 DMA 用的是**总线地址（物理地址）**，不经过 CPU 的页表。如果在 DMA 进行时，操作系统把某一页换出到 swap、迁移到别处，或回收后给了别的进程，网卡就会读写到错误的物理页。所以 `ibv_reg_mr` 要让内核把这些页**钉住**，保证注册期间物理地址不变，再把各页的物理地址写进网卡的翻译表。钉住的页不能被换出，这也是它受 `RLIMIT_MEMLOCK` 约束的原因（本环境 `ulimit -l` 为 unlimited 且有 `IPC_LOCK`，所以测不出这个限制的效果）。

**例外：ODP（On-Demand Paging）**。不钉页，网卡访问到没有映射的页时，由内核处理缺页再通知网卡。本网卡支持 ODP，但本篇的程序**没有使用**，也没有测过它的行为与性能。

**"按页"到底指什么**：

| 问题 | 回答 |
|---|---|
| 网卡的翻译表按什么粒度？ | 以**页**为粒度，默认 4 KiB；用大页时可以更粗 |
| 传给 `ibv_reg_mr` 的 addr、len 必须页对齐吗？ | **不必须**。内核把范围向外取整到页边界，把涉及的**整页**都钉住 |
| 物理页必须连续吗？ | **不必须**。翻译表就是把连续的虚拟地址映射到散落的物理页；所以普通 `malloc` 的内存也能注册 |

**本程序为什么还用 `posix_memalign(4096)`**：对齐不是必须的，只是让首尾不多钉半个页、也不与别的变量共用一页，且区域从页边界开始，便于看地址。

**可靠度**：网卡用物理地址、所以要钉页，以及翻译按页，是 RDMA 的基本机制与公开资料的说法，**推断**；内核里具体调用了哪些函数（如 `pin_user_pages`）同样是依据公开资料的推断，本机未验证。本篇**没有**测过"不钉页会怎样"，也没有测过 ODP。

<a id="3-3"></a>
### 3.3 为什么注册前先写一遍每一页

一句话——Linux 的物理内存是"第一次碰才分配"的，而注册要把每一页都钉住，所以没碰过的页会在注册这一步被迫分配，这部分成本就算进了注册耗时。

1. **`posix_memalign` / `malloc` 只分配虚拟地址**：内核只记下"这段地址归你"，**没有给物理页**，页表项也还没建；
2. **第一次读写某一页时才缺页**：内核分配一个物理页、清零（防止泄露别人的数据）、再映射到你的页表。这就是 first-touch；
3. **`ibv_reg_mr` 要把每一页钉住**，拿到每页的物理地址写进网卡翻译表。没有物理页就没法钉，所以内核得**先替你把这些页缺页分配出来**，每页都要走一遍"分配、清零、映射"；
4. **已经写过的页**已经有物理页，注册只需要钉住并记下地址，开销小得多；
5. **不用 ODP，所以必须在注册时备好**：网卡自己不会处理缺页，所有页都得在注册时由内核准备好。

**对本程序的意思**：注册前已经写满所有页（`fill_pattern` 与 `memset`），所以注册成本**只剩钉页与建表**，量出来的 0.6–0.75 ms 才是注册本身的成本，不混入缺页成本。**不先写也能注册成功，只是更慢**；先写一遍是为了让计时干净，不影响正确性。

**可靠度**：上面的机制解释是**推断**——first-touch 与缺页清零是 Linux 的通用行为，但本篇**没有**对"已触摸 / 未触摸"的注册耗时做对照测量，也没有用 `perf` 或缺页计数验证注册期间究竟发生了多少次缺页；本机透明大页为 `always`，部分页可能是 2 MiB 的大页，每页成本不一定均匀。

<a id="3-4"></a>
### 3.4 注册耗时与收尾顺序

**注册耗时**（128 MiB，注册前已全部写过，**实测**）：

| 运行 | client 的 `ibv_reg_mr` | server 的 `ibv_reg_mr` |
|---|---|---|
| 标准运行 1 | 0.743 ms | 0.706 ms |
| 标准运行 2 | 0.622 ms | 0.649 ms |
| 标准运行 3 | 0.673 ms | 0.634 ms |
| 完整输出那次 | 0.638 ms | 0.648 ms |

绝大多数在 0.6–0.75 ms 之间；另有一次更早的运行里 server 侧出现过 1.800 ms（client 侧同次为 0.700 ms），原因未查明。

**收尾顺序**：程序在**结束时**先 `ibv_dereg_mr` 注销 MR，再 `free(buf)` 释放内存，**顺序不能反**——注销之前，内核还钉着这些页、网卡的翻译表里还记着它们的物理地址，先释放内存就可能让网卡访问到已经还给系统的页。这是 verbs 的标准用法规则；"先释放会怎样"本篇**没有测**。整个销毁顺序是 QP → CQ → MR → PD → 设备，最后才 `free`。

<a id="4-2"></a>
### 4.2 内存布局与数据模式

每端一块 `2 × region` 字节的 buffer，整块注册；`n = region / sizeof(unsigned)`。

| | 区域 `[0, n)` | 区域 `[n, 2n)` |
|---|---|---|
| **client** | 要**写给对端**的数据 A：`A[i] = i*3 + 1` | **读回来**的落点，初始为 0 |
| **server** | 留给 client **写入**，初始为 0 | 给 client **读取**的数据 B：`B[i] = i*5 + 2` |

数据模式用 `unsigned`：每个下标的值唯一，错位也能被发现。`buf` 的类型是 `unsigned*`，所以 `buf + n` 是"跳过 n 个 unsigned"（= `region` 字节），不是跳过 n 字节。

<a id="4-3"></a>
### 4.3 关键代码骨架

```c
/* ===== server-cpu.c（server-1）===== */
posix_memalign((void**)&buf, 4096, total);
memset(buf, 0, region);  fill_pattern(buf + n, n, 5u, 2u);      // [0,n)=0；[n,2n)=B；所有页都被写过
ib_setup(&ib, "mlx5_14", gid_arg, buf, total);                  // 开设备、ibv_reg_mr(主机内存)、建 QP → INIT
bind(eth0 的 IPv4:port) → listen → accept                       // OOB
recv_all(cs, &theirs, ...);  send_all(cs, &mine, ...);          // 交换 conn_info
ib_connect(&ib, &theirs, tc);                                   // QP → RTR → RTS
for (;;) {                                                      // 只响应校验请求
  recv_all(cs, &cmd, 1);
  if (cmd == 'W' || cmd == 'B') { bad = count_bad(buf, n, 3u, 1u); send_all(cs, bad ? "X" : "K", 1); }
  if (cmd == 'Q') break;
}

/* ===== client-cpu.c（server-0）===== */
posix_memalign((void**)&buf, 4096, total);
fill_pattern(buf, n, 3u, 1u);  memset(buf + n, 0, region);      // [0,n)=A；[n,2n)=0
ib_setup(&ib, "mlx5_0", gid_arg, buf, total);
connect(server 的 eth0 IP:port)  /* 没起来就每 100 ms 重试，最多约 30 秒 */
send_all(s, &mine, ...);  recv_all(s, &theirs, ...);  ib_connect(&ib, &theirs, tc);

post_op(&ib, IBV_WR_RDMA_WRITE, l_base, r_base, theirs.rkey, region, 1);  wait_cq(&ib, 1);   // WRITE
send_all(s, "W", 1);  recv_all(s, &ack, 1);                     // OOB：通知 server 校验
post_op(&ib, IBV_WR_RDMA_READ, l_base + region, r_base + region, theirs.rkey, region, 2);  wait_cq(&ib, 1);   // READ
bad = count_bad(buf + n, n, 5u, 2u);                            // 本端校验：直接读本机内存
run_bw(...WRITE...);  run_bw(...READ...);                       // 带宽
send_all(s, "Q", 1);
```

`wr_id`（`post_op` 最后一个参数）只是个标签，会原样出现在完成项里；这里用 1 表示 WRITE、2 表示 READ，方便出错时辨认。`l_base` / `r_base` 是本端 / 对端 buffer 的起始虚拟地址（RDMA 的"本地地址"和"远端地址"都是各自进程里的虚拟地址）。

<a id="4-4"></a>
### 4.4 诊断选项 `-o` 与 `-W`

为了弄清带宽的异常现象（§5.4），`client-cpu.c` 加了两个**正式的诊断选项**，让这些实验可以复现：

| 选项 | 做什么 | 用来回答什么问题 |
|---|---|---|
| `-o RW` / `-o WR` | 在正式步骤之前，按给定顺序**逐次计时**连续 6 次 READ（R）与 6 次 WRITE（W），每次单独 post、单独等完成 | "慢"是只有第一次，还是每次？READ 与 WRITE 哪个有冷启动？ |
| `-W 窗口` | 带宽测试时，每完成"窗口"次操作记一个时间点，结束后打印**逐窗口带宽** | 带宽随时间怎么变？开头有没有预热期？ |

加了 `-o` 之后，后面正式步骤里的"首次 WRITE / READ 耗时"就不再是真正的第一次。逐窗口的时间点在循环里只记录、不打印，结束后才输出，以免干扰测量。

### 5.1 准备与编译

在 nuc 上执行；源码放进两个 Pod 的 `/vllm-workspace`（用 stdin 重定向拷贝，**实测可用**）：

**编译参数**（两个程序的参数完全相同，只是文件名不同）：

| 参数 | 含义 |
|---|---|
| `gcc` | GNU C 编译器。程序是纯 C，用 `gcc`，不需要 `nvcc` |
| `-O2` | 优化级别 2。本程序的瓶颈在 RDMA 与网卡，不在 CPU 计算，`-O2` 足够。用 gdb 单步调试时要换成 `-O0`，否则变量可能被优化掉 |
| `-Wall` | 打开常用警告：未使用的变量、隐式声明、格式串与参数不匹配等 |
| `-Wextra` | 在 `-Wall` 之外再加一批警告：有符号与无符号比较、未使用的函数参数等（并不包含全部警告） |
| `client-cpu.c` / `server-cpu.c` | 源文件 |
| `-o client-cpu` / `-o server-cpu` | 指定输出的可执行文件名；不写则默认生成 `a.out` |
| `-libverbs` | 链接 RDMA 用户态库 `libibverbs`，是 `-l ibverbs` 的连写，不是一个叫 `ibverbs` 的编译选项 |

注意几点：

- **`-libverbs` 要写在源文件之后**：链接器按顺序处理，库放在前面时可能报 `undefined reference to ibv_...`；
- 头文件 `infiniband/verbs.h` 镜像里已预装，不需要额外的 `-I`；不需要 `-lcuda`，也不用 `nvcc`；
- `server-cpu.c` 多用了 `getifaddrs`（取 `eth0` 的 IPv4 地址，头文件 `<ifaddrs.h>`），属于 glibc，仍然只需要 `-libverbs`；
- 源文件开头已经 `#define _GNU_SOURCE`，命令行里不用再写 `-D_GNU_SOURCE`；
- 两个程序在 `-Wall -Wextra` 下**编译通过、没有任何警告**（**实测**）；
- **调试版**：`gcc -g -O0 -Wall -Wextra client-cpu.c -o client-cpu.debug -libverbs`，`server-cpu` 同理（输出 `server-cpu.debug`）。`-g` 生成调试信息，`-O0` 关闭优化；纯 C 程序用普通 `gdb` 即可调试，同样编译通过。

### 5.2 运行


<a id="5-4"></a>
### 5.4 带宽

> 本节有两个容易误读的地方，先说结论：
> **(1)** 流量类别 **TC 对 READ 影响巨大**：`-t 104` 下 READ 从第一次起稳定在 43.8 GB/s，默认 `-t 0` 下不稳定；
> **(2)** **短测试会严重低估 WRITE 带宽**：深度 ≥ 2 时 WRITE 从约 22 GB/s 起步、**逐渐爬升**，要几千次迭代才接近 44 GB/s。

测量口径：单个 QP；一条消息 = 一个完整的 64 MiB 区域；GB/s = 总字节数 / 从第一次 post 到最后一次完成的时间；除特别注明外为 `-n 20` 或 `-n 100`、`-w 8`。

#### 5.4.1 TC 的影响

**默认 `-t 0`，跑 5 次**（`-n 100 -w 8`）：

| 运行 | 首次 WRITE (ms) | 首次 READ (ms) | 带宽 WRITE | 带宽 READ |
|---|---|---|---|---|
| #1 | 3.76 | 12.74 | 22.5 | 24.7 |
| #2 | 1.52 | **103.23** | 22.1 | 24.7 |
| #3 | 1.52 | **96.09** | 22.1 | 24.7 |
| #4 | 1.52 | 39.39 | 22.1 | 24.5 |
| #5 | 1.53 | **102.56** | 22.1 | 24.7 |

**TC=104 与 TC=0 对比**（`-n 100`，两端同设）：

| 配置 | 首次 READ (ms) | 带宽 WRITE | 带宽 READ |
|---|---|---|---|
| `-t 0`，深度 8（上表 5 次） | 12.7 / 103 / 96 / 39 / 103 | 22.1–22.5 | **24.5–24.7** |
| `-t 104`，深度 8，3 次 | **1.55 / 1.55 / 1.55** | 22.1 / 22.1 / 22.1 | **43.8 / 43.8 / 43.8** |
| `-t 104`，深度 1，3 次 | 1.55 / 1.55 / 1.55 | 44.0 / 22.1 / 44.0 | 43.5 / 43.5 / 43.5 |

读法：

1. **READ：`-t 104` 把带宽几乎翻倍（24.6 → 43.8 GB/s），并把第一次 READ 从 12–103 ms 压到 1.55 ms**，3 次完全一致；
2. **WRITE 不受 TC 影响**：深度 8 时两种 TC 都是 22.1 GB/s（这只是短测试的平均值，见 §5.4.2）。

#### 5.4.2 逐窗口的时间曲线（`-W 50`，`-n 600`，深度 8）

| 配置 | 各窗口带宽（GB/s，每窗口 50 次） | 整体平均 |
|---|---|---|
| **WRITE**，`-t 104` | 21.7 22.5 23.6 25.0 26.1 27.2 28.3 29.4 30.5 31.2 32.2 33.1 | 27.1 |
| **WRITE**，`-t 0` | 21.7 22.4 23.5 24.9 26.0 27.1 28.3 29.3 30.4 31.2 32.1 33.0 | 27.0 |
| **READ**，`-t 104` | 43.8 43.8 43.8 43.8 43.8 43.8 43.8 43.8 43.8 43.8 43.8 43.8 | 43.8 |
| **READ**，`-t 0` | 34.2 35.2 36.1 37.2 38.2 38.9 40.0 41.0 **25.4** 40.5 **21.8 17.3** | 31.5 |
| **WRITE**，`-t 104`，**深度 1** | 44.0 44.1 44.1 44.1 44.1 44.1 44.1 44.1 44.1 44.1 44.1 44.1 | 44.1 |
| **READ**，`-t 104`，**深度 1** | 43.5（12 个窗口全部相同） | 43.5 |

读法：

1. **WRITE（深度 8）不是稳态 22 GB/s，而是从约 22 GB/s 起步，逐窗口线性爬升**，600 次后到 33 GB/s 左右，TC 无影响；
2. **深度 1 的 WRITE 从第一个窗口起就是 44.1 GB/s**，毫无爬升；
3. **READ：`-t 104` 恒为 43.8 GB/s；`-t 0` 则不稳**：开头 34 GB/s、缓慢升到 41，随后出现 25.4、21.8、17.3 的骤降。

**更长的运行**（深度 8，`-t 104`，不带窗口）：

| 迭代数 | WRITE 平均 | READ 平均 |
|---|---|---|
| 100 | 22.1 | 43.8 |
| 1500 | 34.3 | 43.8 |
| 6000 | **43.3** | 43.8 |

迭代越多，WRITE 的平均值越接近 44。用"前 100 次约 22 GB/s、其余约 44 GB/s"估算，6000 次的总耗时约 9.27 s，实测 9.30 s，吻合；但 1500 次的估算（约 41 GB/s）与实测（34.3）不符，说明爬升的过程并不是一个干净的阶跃，**确切形状我没有搞清**。

#### 5.4.3 单次操作的逐次计时（`-o`，默认 `-t 0`）

| 顺序 | 连续 6 次 READ（ms） | 连续 6 次 WRITE（ms） |
|---|---|---|
| `-o RW`，运行 1 | **54.62** 3.15 3.15 3.15 3.15 3.15 | 1.53 1.53 1.53 1.53 1.53 1.52 |
| `-o RW`，运行 2 | **28.92** 3.15 3.15 3.15 3.15 3.15 | 1.53 1.53 1.53 1.53 1.53 1.52 |
| `-o RW`，运行 3 | **104.52** 3.14 3.14 3.14 3.14 3.14 | 1.53 1.53 1.53 1.53 1.53 1.53 |
| `-o WR`，运行 1 | **28.59** 3.14 3.14 3.14 3.14 3.14 | 1.52 1.53 1.53 1.54 1.52 1.52 |
| `-o WR`，运行 2 | **41.87** 3.21 3.21 3.21 3.21 3.21 | 1.53 1.53 1.52 1.53 1.53 1.53 |
| `-o WR`，运行 3 | **43.89** 3.15 3.15 3.15 3.15 3.15 | 1.52 1.53 1.52 1.53 1.53 1.53 |

读法：

1. **只有第一次 READ 慢**（29–105 ms），之后稳定在约 3.15 ms（64 MiB / 3.15 ms ≈ 21 GB/s）；
2. **与顺序无关**：不论先做 READ 还是先做 WRITE，第一次 READ 都慢——这是 **READ 特有的冷启动**，WRITE 没有；
3. **WRITE 单次稳定在约 1.52 ms**，折合约 44 GB/s；
4. 这些是默认 `-t 0` 的结果；`-t 104` 下第一次 READ 是 1.55 ms（§5.4.1），这个冷启动**被 TC 消除了**。

#### 5.4.4 这些现象的成因：能说什么、不能说什么

| 现象 | 实测事实 | 成因 |
|---|---|---|
| `-t 0` 下 READ 慢且不稳，`-t 104` 下稳定 | §5.4.1、§5.4.2 | **未查明**。TC 决定报文进入交换机的哪个队列；具体是队列配置、拥塞控制还是别的原因，本篇没有验证（背景见 [roce-swtich.md](roce-swtich.md)） |
| 深度 ≥ 2 时 WRITE 从约 22 GB/s 起步、缓慢爬升；深度 1 则从头到尾 44 GB/s | §5.4.2、§5.4.3 | **未查明**。我检查过 `ethtool -S` 里拥塞、重传、丢弃相关的计数器（含 ECN、CNP 等字样的），深度 1 与深度 8 两次运行里**都没有任何增量**，所以"拥塞控制降速"这个猜测没有证据 |
| 深度 1 时偶尔整个运行都慢（首次 WRITE 3.4–6.2 ms，带宽约 22 GB/s），约 8 次里 1 次 | 深度 1 重复 8 次中有 1 次 22.6；`-t 104` 深度 1 的 3 次里有 1 次 22.1 | **未查明**，像是一种"按进程区分的双峰状态" |

#### 5.4.5 小结

- **同一对网卡、同一条链路，主机内存的 RDMA 能跑到约 44 GB/s（约 352 Gb/s，网卡标称 400 Gb/s 的 88%）**：READ 在 `-t 104` 下任何深度都是 43.8；WRITE 在深度 1 是 44.1，深度 8 在足够长的运行里也平均到 43.3；
- **要得到稳态带宽，测试要足够长**（本篇用 `-n 6000`）。`-n 20`、`-n 100` 的短测试对 WRITE 会严重低估；
- **一定要设 `-t 104`**（两端），否则 READ 会不稳、第一次还要几十毫秒；
- 这些数字**只回答"这个配置、这对网卡、这条路径"下的带宽**：单 QP、单条 64 MiB 消息，不是网卡能力的上限（多 QP、多消息尺寸都没测）。

### 5.5 数据走了哪条路：字节计数器

方法：取一次运行前后 `ethtool -S` 的 RDMA vport 计数器与 `eth0` 字节数的差值。本次 `-n 20`、`-t 104`（共 21 次 WRITE + 21 次 READ，每次 64 MiB，即各 1344 MiB 净载荷）（**实测**）：

| 计数器 | server-0（client，`fabric0`） | server-1（server，`fabric14`） |
|---|---|---|
| RDMA 发出 `tx_vport_rdma_unicast_bytes` | **1375.326 MiB** | **1369.850 MiB** |
| RDMA 收到 `rx_vport_rdma_unicast_bytes` | **1369.850 MiB** | **1375.326 MiB** |
| `eth0` 发出（OOB） | 0.002 MiB | 0.001 MiB |
| `eth0` 收到（OOB） | 0.001 MiB | 0.002 MiB |
| `fabric` 内核网口 `tx_bytes` | 0.000 MiB | 0.000 MiB |

读法：

1. **RDMA 流量约 1.3 GiB，与理论净载荷相符**，多出的约 2% 应是协议头、确认包和 READ 请求（**推断**，未拆分）；
2. **两端互相印证**：client 发出的 1375.326 MiB 恰好等于 server 收到的，client 收到的 1369.850 MiB 恰好等于 server 发出的；
3. **`eth0` 上只有约 1–2 KiB**：OOB 只传控制信息；
4. **`fabric` 的内核网口计数为 0**：RDMA 流量绕过了内核网络栈。

`ethtool` 不在镜像里，取证前要在 Pod 里装（`apt-get install ethtool`，只影响容器层）。这些计数器能证明"数据确实经 RoCE 的 RDMA 通道传输、`eth0` 上没有数据"。

<a id="5-6"></a>
### 5.6 单边操作：CPU 在干什么

RDMA 的 WRITE / READ 是单边操作，**对端的 CPU 不参与**。这点可以直接测：让 client 连续做 6000 次 WRITE + 6000 次 READ（约 20 秒，`-t 104`），中途在两个 Pod 里各采样一次进程的累计 CPU 时间（`/proc/PID/stat` 的 utime + stime），间隔约 5.7 秒（**实测**，含 `kubectl exec` 的延迟，是估算）：

| 进程 | 采样间隔内增加的 CPU 时间 | 约占一个核的 |
|---|---|---|
| `server-cpu`（server-1，被动方） | **0.04 s** | **约 1%** |
| `client-cpu`（server-0，主动方） | 5.62 s | 约 98% |

**server 在自己的内存被以约 43 GB/s 的速度读写的同时，CPU 几乎完全空闲**（它阻塞在等 OOB 命令的 `recv` 上）。client 约 98%，是因为它在**忙轮询**完成队列（`ibv_poll_cq` 循环）。

## 6. 速查：命令与坑

```bash
# 编译（纯 C，不需要 nvcc / CUDA）
gcc -O2 -Wall -Wextra client-cpu.c -o client-cpu -libverbs
gcc -O2 -Wall -Wextra server-cpu.c -o server-cpu -libverbs

./client-cpu -a <IP> -t 104 -n 6000 -w 8

./client-cpu -a <IP> -t 104 -n 600 -W 50               # 逐窗口带宽
./client-cpu -a <IP> -o RW                             # 逐次计时（READ 的冷启动）
```

| # | 坑 / 注意 | 说明 |
|---|---|---|
| 1 | **一定要设 `-t 104`，两端都要设** | **实测**：默认 `-t 0` 下，READ 第一次要 12–103 ms、稳态只有约 24.6 GB/s 且会骤降；`-t 104` 下 1.55 ms、43.8 GB/s、完全稳定。运行 NCCL 同理，必须 `NCCL_IB_TC=104` |

| 3 | 第一次 READ 是冷启动 | **实测**：`-t 0` 下第一次 READ 慢几十毫秒，之后稳定在约 3.15 ms；不要把第一次的耗时当作 READ 的典型延迟 |
| 4 | 注册前要先写一遍每一页 | 未触摸的页由注册那一步补物理页，注册会变慢（**推断**，§3.3）。本程序填数据时已经写满 |

| 6 | 先注销 MR，再释放内存 | 顺序不能反（§3.4） |
| 7 | 两端的 `-s` 必须一致 | 否则在交换连接信息时退出 |
| 8 | server 要先启动 | client 对连接做了重试（每 100 ms，最多约 30 秒）。从 nuc 在后台起 server 时，不要用 `kubectl exec … 'setsid nohup ./server-cpu … & echo started'`（实测会挂住约 5 分钟），而是把 `kubectl exec … ./server-cpu` 命令本身放进后台（`... > log &`），再轮询日志里的"OOB 监听" |
| 9 | 只能用偶数号网卡 | `mlx5_0/2/…/14`；`/dev/infiniband` 下只有偶数号的 `uverbs`，用奇数号网卡预计会找不到设备或打开失败（**推断**，未试过；程序对此有报错提示） |
| 10 | 没有控制 NUMA 亲和性 | 程序没有绑核、没有指定内存所在的 NUMA 节点，主机内存与网卡的位置关系会影响结果，本篇未测 |

| RDMA 流量约 1.3 GiB，与理论净载荷相符，两端互相印证；`eth0` 约 1–2 KiB；`fabric` 内核网口为 0 | **实测**（`ethtool -S` vport 计数器） |
| `server-cpu` 在传输期间 CPU 约 1%，`client-cpu` 约 98% | **实测**（采样间隔约 5.7 s，含 `kubectl exec` 延迟，是估算） |
| `conn_info` 为 48 字节（各字段偏移见 §2.2） | **实测**（Pod 内编译，`sizeof` / `offsetof`） |
| OOB 上交换的内容：一次 `conn_info` + 1 字节命令 `W`/`B`/`Q` 与回复 `K`/`X` | **代码事实**；`eth0` 流量约 1–2 KiB 与之量级吻合，**未逐包核对** |
| 连接 = 两端 QP 互相配置对方的 `qpn` / `psn` / `gid` 并到 RTS；`addr` + `rkey` 属内存授权、每次操作才用 | **代码事实**（`ib_connect`、`post_op`） |
| 手工 `modify_qp` 建连时不发握手包，填错信息到第一次操作才暴露；中途关闭 TCP 的影响 | **推断** / **未测**（未抓包、未故意填错） |
| `-t` 写入 QP 的 `grh.traffic_class`，高 6 位为 DSCP（104 → DSCP 26） | **代码事实**；DSCP 换算按字段定义，**未抓包验证** |
| READ 的数据带的是 server 端 QP 的 traffic class，所以 READ 需两端都设 | **推断**（RoCE 机制）；只设一端的情形**未测** |

**注册与钉页**

| 结论 | 状态 |
|---|---|
| 网卡 DMA 用物理地址，所以注册要钉页；翻译表按页（默认 4 KiB）；addr/len 不必页对齐、物理页不必连续 | **推断**（RDMA 基本机制与公开资料），本机未直接验证 |
| 注册前先写一遍每一页可避免把补页成本算进注册；未触摸页注册慢是因为内核要先缺页分配 | **推断**（Linux 通用机制；本篇没有"已触摸 / 未触摸"的对照测量，也未用 `perf` / 缺页计数验证） |
| 先注销 MR 再释放内存是 verbs 的标准用法；先释放会怎样 | 规则为**公开资料**；后果**未测** |

**明确没有测的**

| 项目 |
|---|
| 多 QP、不同消息大小、不同区域大小对带宽的影响 |
| 主机内存与网卡的 NUMA 亲和性；大页（透明大页为 `always`，但没有对比关闭时的情形） |
| 交换机侧 PFC / ECN 配置；TC 为何对 READ 敏感 |
| 多个并发连接；client 或 server 异常退出时的行为 |
| 不钉页（不注册）直接 RDMA 会怎样；ODP 的实际使用（网卡支持，本篇未使用） |
