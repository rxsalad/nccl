### 0.1 测量方法（每脚本三段式）

1. **语义正确性**：小张量（4 元素）上验证严格定义，期望值可人工核对（如 [36,72,108,144] = (1+2+…+8)×[1,2,3,4]）；
2. **耗时**：大张量（16 GB 级，十进制）× 5 次迭代，CUDA event 计时。**口径说明**：本手册耗时为 5 次连发平均（含稳态流水），孤立单次执行约慢 ~7%（broadcast 实测：5 连发 23.5 ms 对孤立 25.06–25.20 ms）——字节不受影响、时间略乐观；
3. **流量对账**：每 GPU NVLink 累计 Tx（`nvidia-smi nvlink -gt d`，全链路求和）前后差值 ÷ 迭代数（节点 Tx 合计 = Rx 合计，只看 Tx；计数器为节点历史累计值，取差值即可）。口径：度量的是**整个迭代窗口的总差值 ÷ 次数 = 每次平均**，不是抽测其中一次——窗口前后有 barrier + synchronize 隔离，warmup 与语义验证的流量不计入；耗时（ms）也是同一窗口的平均，两个指标测的是**同一批迭代**。

统一运行方式（Pod 内）：`torchrun --nproc_per_node=8 <op>.py`。

<a id="s-0-2"></a>
### 0.2 测量纪律（实测教训）

1. **同节点同时刻只跑一个 NCCL 测量任务**——GPU 与 NVLink 计数器必须独占；曾有并发 debug 任务与基准并行，使 reduce 实测字节恰好翻倍（比值 2.000）、耗时劣化 5 倍，两个操作数据作废重跑。抓日志/证据类任务一律排在测量之后串行执行。
2. **变长 a2a 每个模式用独立进程测首窗**——同进程切换模式会带入确定性超额流量（详见 all_to_all 节的分析⑤）。
3. **路径一致性（实测，broadcast）**：担心的场景是"5 次迭代混走不同路径"。机制上不会——通道图在通信器建立时定死（Trees 日志仅 init 打印一次），算法/协议按调用选择但只依赖 (op, size, 拓扑)，无历史/随机；实测亦证：5 次独立单次运行（iters=1）字节**逐次完全相同**（min/max 亦同；早期 GiB 口径实验，数据见过程记录）。**一个真实口径差**：连发窗口测的是稳态吞吐（相邻操作在组内/内核级流水重叠），孤立单次略慢——broadcast 5 连发平均 23.5 ms 对孤立单次 25.06–25.20 ms，差 ≈7%；**字节不受影响，时间略乐观**。
4. **warmup 3 次的适用范围**：对本手册全部操作足够（字节与分布在全部实验中逐位稳定）；例外是变长 a2a 的模式切换（见第 2 条）——warmup 加到 20 也吸收不了，只能换进程。

<a id="s-0-3"></a>
### 0.3 约定

- **单位**：尺寸、流量、带宽一律十进制——**GB = 10⁹ B、GB/s = 10⁹ B/s**；NVLink 计数器原始读数为 KiB（2¹⁰ B），按 KiB×1024/10⁹ 换算为 GB。
- **记号**：**rank 与 GPU 统一用 0–7**——GPU k = rank k = `cuda:k` = `nvidia-smi` 输出的 `GPU k`，一套编号贯穿全文、无需换算。严格定义与代码用 rank 记号（`x_0…x_7`、`src=0`/`dst=0`），原理走读用 GPU 记号（GPU0 即 rank 0）。
- **尺寸记号**：S = 每 rank 输入字节；C = 每 rank 块/段字节（AG 的输入块、RS 的输出段）。

<a id="s-0-4"></a>
### 0.4 环形字节模型（对账基准）

W 个 rank，每次操作**每卡发送量**：

| 操作 | 每卡发送量 | W=8 时 | 说明 |
|---|---|---|---|
| broadcast / reduce | (W−1)/W × S | 0.875×S | S = 消息字节数 |
| all_reduce | 2(W−1)/W × S | 1.75×S | = RS + AG |
| all_gather | (W−1) × C | 7×C | C = 每 rank 输入块，输出 8C |
| reduce_scatter | (W−1) × C | 7×C | C = 输出段，输入 8C |
| all_to_all（等分） | (W−1)/W × S | 0.875×S | 每 rank 发 S/8 给其余 7 卡 |

系数中的 **(W−1)，"−1"即"不发给自己"**——每个 rank 对自己那份是本地/原地数据，不产生线上字节；这也是 8 卡下 7/8 = 0.875、2×7/8 = 1.75 的由来。

<a id="s-0-5"></a>
### 0.5 算法指纹与结构

**算法指纹（实现判定的共性判据）**：同一操作可由多种算法实现，且多种算法**总字节往往相同**——均值对账只能验证总量、不能区分实现；判定靠"**每卡字节均值 + 每 GPU 分布形状**"双判据：

| 算法 | 每卡发送量 | 分布形状 |
|---|---|---|
| Ring（无死边：AG/RS） | = 环形模型 | 人人均匀 |
| **Ring（含死边：broadcast/reduce）** | = 环形模型 | **min ≈ 0（死边发送方）/ max = S** |
| 树（Tree） | 均值 = 环形模型 | 不均：近根卡最多 2 份 |
| NVLS（交换芯片归约/多播扇出） | **远低于环形模型** | 均匀 |

**Ring 的死边效应（broadcast/reduce 的"链形"分布来源）**：Ring 是**闭合回路**（0→1→…→7→0，8 条边），但不同操作语义会在环上产生**死边**（不载货的边）——数据沿环流动时，某一条边恰好"不需要搬"：

- **broadcast**：死边 = **指向 src** 的环边（7→0）——src 本来就有数据，上家只收不发（`broadcast.h`：`nextRank == root → directRecv`）→ 每 GPU 发送量分布 = [S×7, 0]（GPU7 = src 的上家，不发）。
- **reduce**：死边 = **dst 的出边**（0→1）——dst 只收不发（`reduce.h`：dst `recvReduceCopy`，不加转发）→ GPU0 = dst，不发。
- **AG / RS**：**无死边**——任何块/段都要送达其余全部 rank，没有"绕回自己"的边 → 人人均匀。

死边位置**随 src/dst 变**——换 src/dst 则轮空的 GPU 换人（结构副产物，非设计）。**broadcast 与 reduce 是同一棵 Ring 图、仅死边位置不同**（broadcast 死边在 src 上家、reduce 死边在 dst 自身出边）。

**环算法的轮次机制**（AG/RS/环形 AR 共用；以 4 卡环、每人 1 块 A/B/C/D 为例）：

```
第 1 步: 0─A→1  1─B→2  2─C→3  3─D→0     （人人发自己的块）
第 2 步: 0─D→1  1─A→2  2─B→3  3─C→0     （转发上一步刚收到的块）
第 3 步: 0─C→1  1─D→2  2─A→3  3─B→0
→ N 卡环 N−1 步后, 人人拥有全部块
```

每步人人同时收发 1 块（全双工、无空闲）——不是"一块数据转圈"：每块只走 **N−1 跳**（恰好差一跳回到起点——起点本来就有，回去是浪费），且任意时刻 N 条链路全部满载（所有块同时在途、相位错开）。三重保证：**拓扑**——环上走 N−1 跳必经其余所有成员（数学性质，不会漏）；**依赖**——收到才能转发，数据依赖链天然定序（不会乱）；**落位**——来自 rank j 的块写入输出第 j 槽（拼得对）。字节账：每卡每步 1 块 × (N−1) 步 = **(N−1)×C**，即环形模型。

**reduce_scatter 是同一轮次的"边加边转发"变体**：每步转发的不是块、而是**累积中的部分和**（收到 → 加上自己的贡献 → 转发）。每卡**经手所有段**、为 N−1 个段各贡献一次加法（计算摊开在别人段上），只有"最后一加"恰好落回自己段（绕一圈回来的部分和 + 自己）——所以输出只有自己那段。与"数据直达目的地、目标卡独算"的 a2a 式实现相比：计算总量相同（每卡 (N−1)×C），只是**环形摊开、a2a 式集中**。

**通道结构（共性事实）**——NCCL 的通道是**同一棵逻辑图的并发副本**：

- **一次定死**：通道图在通信器建立时一次性计算，通道不各自选路、不轮换 GPU 顺序；通道只决定搬运哪一份（如 1/32）数据——**改变并发度、不改变算法形状与字节**（各节通道扫描反复证实）。
- **同构（日志核实）**：32 条通道完全同构——broadcast/reduce 与 AG/RS 的环序均为 `0 1 2 3 4 5 6 7`（32 × `Channel xx/32 : 0 1 2 3 4 5 6 7`）。broadcast/reduce 的**死边**（7→0 / 0→1）造成 min≈0/max=S 分布；AG/RS 无死边、人人均匀——分布指纹由此区分。
- **Trees 日志的角色**：通信器同时建立树图资源（`Trees [0]` 日志）——这是**可用资源**，供 all_reduce 等树算法使用；broadcast/reduce **不走树**（源码 `tuning.cc:274` 只允许 Ring），走的是 Ring 通道（`Channel c/32` 日志）。单节点时树图恰为线性链 0–1–…–7（与 Ring 环序一致），但 broadcast 的"链形"分布来自 Ring 死边、不来自树。
- **全互联无争用**：NVLink 任意两卡 NV18 直连，Ring 的每一跳走专属直达链路、互不争用。

<a id="s-0-6"></a>
### 0.6 带宽指标（algbw / busbw / 线上实际速率）

| 指标 | 定义 | 回答的问题 |
|---|---|---|
| **algbw**（算法带宽） | S_alg ÷ t | **语义层**：每秒完成多少有效数据 |
| **busbw**（总线带宽） | 环形模型每卡发送量 ÷ t（= algbw × 环形系数） | **归一化层**：若按环形实现，每卡线上每秒跑多少字节 |
| 线上实际速率 | NVLink 实测每卡 Tx ÷ t | **物理层**：线上真的跑了多少（本手册实测项，NCCL 自身不输出） |

- **S_alg 的取法**（与 nccl-tests 惯例一致）：取该操作对每 rank 处理的完整张量——AR/broadcast/reduce/a2a 取输入 S；all_gather 取输出总量（8C）；reduce_scatter 取输入总量（8C）。
- **为什么需要 busbw**：algbw 跨操作不可直接比——同样的 algbw，AR 语义在线上要搬 1.75 份、AG 只搬 0.875 份（环形口径）；乘上环形系数后，不同操作、不同卡数（(W−1)/W）、不同实现被折到同一把尺子上。
- **busbw 是归一化指标，不是测量值**：只在**无死边 Ring** 下 busbw = 实际线速；其他算法下是"环形等效"——Ring 含死边（broadcast）：busbw 595 **低于**实际线速 680（每卡实发 S，是环形口径 7/8×S 的 8/7 倍）；NVLS（all_reduce，16 GB）：busbw 842 **高于**实际线速 541（每卡实发 1.125×S，只有环形口径 1.75×S 的 0.643）。**busbw 与实测线速的偏差方向本身就是算法指纹**。
- **饱和判断用 busbw 对链路峰值**：强制 Ring all_reduce（16 GB）busbw 697 GB/s（28.0 GB ÷ 40.2 ms），为 NV18 方向峰值 956 GB/s 的 73%。

## 1. broadcast（广播）

[↑ 返回目录](#目录)


**严格定义**：`out_r = x_src`（∀r，含 r = src）——src rank 的张量**逐元素复制**到每一个 rank；W=8、src=0 时，8 个 rank 全部持有 rank 0 的原张量。语义上包含 src 自己，但对自己是恒等——**不给自己拷贝**，线上只送其余 7 份。

**原理走读（以 8 卡为例）**：

- **做什么**：GPU0（src）持有 `(a, b, c, d, e, f, g, h)`，其余 7 卡为空 → 操作后 8 张卡都持有同一份。
- **怎么做**：消息均分成多份、**多条同构的 Ring 并发**（NCCL 通道；具体条数与配置相关，本机默认 32，见分析③），每条 Ring 各传其中一份；Ring 内逐跳转发（`GPU0 → GPU1 → … → GPU7`）、**死边 7→0 不载货**（GPU7 只收不发），Ring 间并发。
- **通信开销**：总发送 = 7 份 S = 7S，平均每卡 7/8 × S = 0.875×S——系数 (W−1) 的"−1"就是"不给自己拷贝"。

**形象介绍**：主持人要让人手一份讲稿。星形：主持人挨个抄 7 遍——瓶颈在主持人；单队传阅：排成一队逐人传抄——瓶颈在队伍长度（7 跳串行）；NCCL 的做法：**稿子裁成多叠、多支队伍同时传阅**——每队只传其中一叠，队伍长度不再是瓶颈。

**PyTorch 代码**：`sn-codes/broadcast.py`（单文件，三段式：① 小张量语义验证，结果可心算 → ② 16 GB × 5 次迭代计时 → ③ NVLink Tx 前后差值对账模型）。运行（Pod 内）：`cd /tmp/sn-codes && torchrun --nproc_per_node=8 broadcast.py`。

**运行**（实测）：

```
=== broadcast（广播） ===
[语义] PASS: 8 个 rank 全部得到 src=0 的 [1,2,3,4]
[规模] src(rank0) 持有 16 GB, 广播到 8 卡; 迭代 5 次
[耗时] 每次 23.542 ms | algbw 680 GB/s | busbw(环形口径) 595 GB/s
[流量] NVLink 实测: 每 GPU 平均 14.0017 GB/次 (min 0.0010 / max 16.0020)
[对账] 环形模型 14.0000 GB/次/GPU -> 实测/模型 = 1.000
```

**分析**：

**① 字节总量对账**：模型 0.875×S = 14.0000 GB/卡/次，实测 14.0017 GB（1.000；+1.7 MB 为协议开销）。均值不区分实现（Ring 含死边/无死边/树总字节同为 7S；判据见第 0 节算法指纹表），判定看分布。

**② 算法判定 = Ring（含死边；分布 + 源码双证据）**：实测三项特征——min = 0.0010 GB ≈ 0、max = 16.0020 GB = S、均值 = 7/8×S，对照第 0 节指纹逐一排除：**无死边 Ring** ❌（要求人人均匀 14 GB，实测 min≈0）；**二叉树** ❌（root 应发 2 份、max = 2S = 32 GB，实测 max = S）；**NVLS** ❌（多播扇出均值应 = S/8 = 2 GB，实测 7/8×S）；**Ring 含死边** ✓（死边 = 指向 src 的环边 7→0、src 上家 GPU7 不发——min≈0；其余 7 卡各发一份 max=S；均值不变）。源码实锤：`tuning.cc:274` broadcast **只允许 Ring**（无独立"链"算法）；`broadcast.h` 只实现 Ring × 3 协议。

**③ 并发结构 = 32 条同构 Ring（通道扫描实测）**：强制 `NCCL_MAX_NCHANNELS`：

| 通道数 | 1 | 2 | 4 | 8 | 16 | 32（默认） |
|---|---|---|---|---|---|---|
| algbw (GB/s) | 26 | 51 | 102 | 203 | 397 | **680** |

  每条通道 ≈26 GB/s、**线性扩展**；单通道时字节与分布不变（14.0017 GB、min≈0/max=S），仅耗时 23.5 ms → 624 ms（×26.5）——通道只改并发度（共性见第 0 节通道结构）。broadcast 特有的反证：若 32 条通道的环序轮换死边位置，每卡在多数通道转发、字节趋近均匀（≈15.5 GB/卡）——分布会长得**像无死边 Ring**，实测 min≈0/max=S 排除（单节点 32 通道环序全同、死边恒在 GPU7）。

**④ 性能**：23.542 ms 搬 16 GB——每卡线速 ≈ 16.0 GB / 23.5 ms ≈ **680 GB/s** = 32 通道并发 × ≈26 GB/s；Ring 的串行逐跳（含死边的 7 跳路径）被通道内流水 + 通道间并发掩盖。busbw（环形口径 595 GB/s）偏低 8/7：含死边 Ring 的每卡实发（S）是环形口径（7/8×S）的 8/7——busbw 是归一化指标而非实测线速（定义见第 0 节）。

## 2. reduce（归约到一卡）

[↑ 返回目录](#目录)


**严格定义**：`out_dst[i] = Σ_{r=0}^{W-1} x_r[i]`——逐元素求和，**只有 dst rank 持有结果**；其余 rank 的输出缓冲无定义（这也是它与 all-reduce 的唯一区别）。

**原理走读（以 8 卡为例）**：

- **做什么**：GPU_i 各持 `(a_i, b_i, c_i, d_i, e_i, f_i, g_i, h_i)`（i=0..7）→ 操作后**仅** GPU0（=dst）持有 `(a0+…+a7, b0+…+b7, …, h0+…+h7)`，其余卡输出无定义。
- **怎么做**：与 broadcast 完全同构（同一个 Ring、死边换位置）——消息均分成多份、**多条同构的 Ring 并发**（第 1 节），Ring 内逐跳、Ring 间并发；方向相反：数据沿环**下行汇聚**（每卡发给 r−1，`GPU7 → GPU6 → … → GPU0`），**死边 0→1 不载货**（dst=GPU0 永不发送），每个接收 rank 就地"收到的部分和 + 自己的输入"相加再往下传（边搬边算）。
- **通信开销**：与 broadcast **镜像对偶**——同一个 Ring、死边从 7→0 换到 0→1，总量逐项相同：总发送 7 份 S = 7S，平均每卡 7/8 × S = (W−1)/W × S。

**形象介绍**：8 个分店各有账本，要算出总账送到总部。星形是总部挨个收（总部淹死）；链式接力是每家只把"收到为止的部分和"传给下一家，传到队尾总账正好攒齐、送到总部手里。

**PyTorch 代码**：`sn-codes/reduce.py`（单文件，三段式：① 小张量语义验证（仅 dst 可验，flag 求和期望 = 1）→ ② 16 GB × 5 次迭代计时 → ③ NVLink Tx 差值对账模型）。运行（Pod 内）：`cd /tmp/sn-codes && torchrun --nproc_per_node=8 reduce.py`。

**运行**（实测）：

[耗时] 每次 23.332 ms | algbw 686 GB/s | busbw(环形口径) 600 GB/s

[对账] 环形模型 14.0000 GB/次/GPU -> 实测/模型 = 1.000

**分析**：

**① 字节总量对账**：模型 0.875×S = 14.0000 GB/卡/次，实测 14.0017 GB（1.000；+1.7 MB 协议开销）。均值不区分实现（指纹见第 0 节），判定看分布。语义验证只能在 dst 做（非 dst 输出无定义——脚本 flag 求和期望 = 1）；在定义族中与 broadcast（第 1 节）成对：一个散（1 → 全员）、一个汇（全员 → 1）。

**② 算法判定 = Ring（含死边；分布 + 源码）**：实测 min = 0.0010 GB ≈ 0、max = 16.0020 GB = S、均值 = 7/8×S——与 broadcast **完全同构（镜像）**：同一个 Ring、死边换位置——**reduce 死边 = dst 的出边 0→1**（GPU0 = dst 永不发送），数据沿环**下行汇聚**至 GPU0。源码：`reduce.h` `runRing`——dst `recvReduceCopy`（只收不加转发）、其余 `recvReduceSend`（边收边加边转发）。对照第 0 节指纹：无死边 Ring ❌（应均匀 14 GB）、二叉树 ❌（max 应 2S）、NVLS ❌（无 NVLS comm 行）；**Ring 含死边 ✓**。

**③ 并发结构 = 32 条同构 Ring（通道扫描实测）**：强制 `NCCL_MAX_NCHANNELS`：

**④ 性能**：23.332 ms 搬 16 GB——与 broadcast（23.542 ms）耗时几乎相同：同一个 Ring、同样的字节，只差方向（散对汇）。Ring 形状决定性能（每卡线速 ≈ 16.0/23.3 ≈ **686 GB/s**）；方向只有微小影响——**下行略快于上行**：单通道 35 对 26 GB/s（+35%）、32 通道 685 对 680（+0.7%）——方向性不对称的机制未深挖（见未验证项）。**计算免费**：与 broadcast 的本质区别是 reduce 边搬边算——每个接收 rank 在通信内核里就地加（收到的部分和 + 自己的输入），算术强度仅 0.25 FLOP/B、本地多读一份输入（16 GB HBM，TB/s 级）远快于线上（680 GB/s）——**带着计算不慢反快**（23.3 对 23.5 ms）。

## 3. all_gather（全收集）

[↑ 返回目录](#目录)


**严格定义**：`out_r = concat(x_0, x_1, …, x_{W-1})`（∀r）——**拼接不求和**，每个 rank 持有全部 rank 的块按 rank 序排好的完整张量。

**原理走读（以 8 卡为例）**：

- **做什么**：GPU0: `(a)`、GPU1: `(b)`、GPU2: `(c)`、…、GPU7: `(h)` → 8 张卡都持有 `(a, b, c, d, e, f, g, h)`（只拼接、不求和）。
- **怎么做（环形）**：**多条同序的环并行**、各搬一份（第 0 节通道结构）——每条环只搬消息的一个分片（各环分片互不重叠、合并恰为完整消息）；环内，各卡把自己的块沿环逐跳传递——每过一跳就多攒到一块，7 轮后人人凑齐，每卡发出的都是**自己那块**的 7 份拷贝（经环替别人捎带）。全部环完成时每卡自然拥有全部数据——无需任何"最后合并"步骤。
- **通信开销**：每卡 7 × 块 = (W−1)×C = (W−1)/W × 拼接后总量。

**形象介绍**：拼图——8 个人每人手里一块拼图，结束时每人手里都有拼好的完整 8 块（自己那块不动，经手别人的 7 块）。与 reduce（第 2 节）不同：不做加法、只拼接；"别人的 7 块"都要过一遍手，这就是 7×C 的来源。

**PyTorch 代码**：`sn-codes/all_gather.py`（单文件，三段式：① 小张量语义验证 → ② 16 GB 级 × 5 次迭代计时（输入块 2 GB，输出 16 GB）→ ③ NVLink Tx 差值对账模型）。运行（Pod 内）：`cd /tmp/sn-codes && torchrun --nproc_per_node=8 all_gather.py`。

**运行**（实测）：

```

[语义] PASS: 每 rank 拼出 [1,1,1,1,2,2,2,2,...,8,8,8,8]
[规模] 每 rank 输入块 2 GB, 输出 16 GB; 迭代 5 次
[耗时] 每次 25.708 ms | algbw 622 GB/s | busbw(环形口径) 545 GB/s
[流量] NVLink 实测: 每 GPU 平均 14.0009 GB/次 (min 14.0009 / max 14.0009)
[对账] 环形模型 14.0000 GB/次/GPU -> 实测/模型 = 1.000
```

**分析**：

**① 字节总量对账**：模型 7×C = 7×2 GB = 14.0000 GB/卡/次（C = 每 rank 输入块，输出总量 8C = 16 GB），实测 14.0009 GB（1.000；+0.9 MB 协议开销）。

**② 算法判定 = Ring（分布 + 排除法）**：分布**完全均匀**（min = max）排除树与 Ring 含死边（两者分布均不均匀）；字节 = 模型排除 NVLS（NVLS 下每卡应**远低于**模型——多播发一份即够，第 0 节指纹；且日志无 NVLS comm 行）——**无死边 Ring ✓**。与 reduce/broadcast 的对照最能说明问题：**同一个通信器、同一棵可用树图**（Trees 日志在全部操作中完全相同），调优器却为 AG 选了环——算法选择**按操作逐个**做，树图存在不等于使用。

**③ 并发结构 = 32 通道（通道扫描实测）**：强制 `NCCL_MAX_NCHANNELS`：

| 通道数 | 1 | 2 | 4 | 8 | 16 | 32（默认） |
|---|---|---|---|---|---|---|
| algbw (GB/s) | 28 | 55 | 108 | 209 | 385 | **622** |

  每通道 ≈27 GB/s、1→16 通道**线性**；16→32 亚线性（+62%，逼近 NVLink 单向饱和）。通道只改并发度（共性见第 0 节）。

**④ 性能**：25.708 ms——每卡线速 14.0/25.7 ≈ **545 GB/s**；algbw 622 GB/s 按输出总量（16 GB）计。环形实现下 busbw = 实际线速（第 0 节三层指标在此重合）。**变长版 `all_gatherv`**：允许各 rank 块大小不等（如各 rank 持有的 token 数不同），环形字节模型不变、按实际块大小加权。

## 4. reduce_scatter（归约散射）

[↑ 返回目录](#目录)


**严格定义**：`out_r = (Σ_{k=0}^{W-1} x_k) 的第 r 段`——先求和再按段切分，**每 rank 只拿自己那 1/W 段**，各段互不重叠。all_gather 的逆方向（AG 拼不消和，RS 消和不拼）。

**原理走读（以 8 卡为例）**：

- **做什么**：每卡持 8 段——GPU_i: `(A_i, B_i, …, H_i)`（i=0..7）→ GPU0 得 `(A0+…+A7)`、GPU1 得 `(B0+…+B7)`、…、GPU7 得 `(H0+…+H7)`——**每卡只拿自己下标的那一段和**。
- **怎么做**：**多条同序的环并行**、各搬一份（第 0 节通道结构）；环内，各卡对各段的部分和沿环逐步合并、落位到持有该下标的卡——只合并、不拼齐。
- **通信开销**：每卡 7 × 段 = (W−1)×C = (W−1)/W × 输入总量；与 all_gather 字节相同、方向相反（互为镜像）。

**形象介绍**：分段收账——总账算出来**不发给任何人**：每人只拿走自己负责的那 1/8 段（先在段上把账算清、再各自取走自己的段）。

**PyTorch 代码**：`sn-codes/reduce_scatter.py`（单文件，三段式：① 小张量语义验证 → ② 16 GB 级 × 5 次迭代计时（输入 16 GB，输出 2 GB）→ ③ NVLink Tx 差值对账模型）。运行（Pod 内）：`cd /tmp/sn-codes && torchrun --nproc_per_node=8 reduce_scatter.py`。

**运行**（实测）：

```

[规模] 每 rank 输入 16 GB, 输出 2 GB; 迭代 5 次
[耗时] 每次 20.234 ms | algbw 791 GB/s | busbw(环形口径) 692 GB/s
[流量] NVLink 实测: 每 GPU 平均 14.0009 GB/次 (min 14.0009 / max 14.0009)
[对账] 环形模型 14.0000 GB/次/GPU -> 实测/模型 = 1.000
```

**分析**：

**① 字节总量对账**：模型 7×C = 14.0000 GB/卡/次（C = 输出段 2 GB，输入总量 8C = 16 GB），实测 14.0009 GB（1.000）。

**② 算法判定 = Ring（分布 + 排除法）**：与 all_gather 完全同构——均匀（min = max）排除树与 Ring 含死边、字节 = 模型排除 NVLS（实测恰为模型值，且无 NVLS comm 行）——**无死边 Ring ✓**。与 AG 互为镜像：一个"凑齐"、一个"还回"，字节与时间都几乎对称（14.0009 对 14.0009）。

**③ 并发结构 = 32 通道（通道扫描实测）**：强制 `NCCL_MAX_NCHANNELS`：

  1→16 通道**严格线性**（每通道 ≈37 GB/s——比 all_gather 的 ≈27 高约 37%，同为环、方向相反，每通道速率不同，未深挖）；16→32 亚线性。通道只改并发度（共性见第 0 节）。

**④ 性能**：20.234 ms——**algbw 791 GB/s 为七种操作最高**：同样的线上字节（14 GB/卡）搬运了 8 倍的算法层字节（输入 16 GB 摊平读、输出只写 2 GB，推断）；每卡线速 14.0/20.2 ≈ **692 GB/s** = busbw（环形实现下两者重合）。**变长版 `reduce_scatterv`**：`all_gatherv` 的对偶（段大小不等），字节模型按实际段大小加权。

## 5. all_reduce（全归约）

[↑ 返回目录](#目录)


**严格定义**：`out_r[i] = Σ_{k=0}^{W-1} x_k[i]`（∀r）——逐元素求和，且**每个 rank 都持有完整结果**。语义 = reduce（第 2 节）+ broadcast（第 1 节）；环形实现 = reduce_scatter（第 4 节）+ all_gather（第 3 节）。

**原理走读（以 8 卡为例）**：

- **做什么**：GPU_i 各持 `(a_i, b_i, …, h_i)`（i=0..7）→ **每张卡**都得到同一个聚合向量：

  ```
  GPU0..7（全部相同）: (a0+a1+…+a7, b0+…+b7, c0+…+c7, …, h0+…+h7)
  ```

- **怎么做（两条路）**——不把数据都发给某个中心节点（那会成为瓶颈）：
  - **环形两阶段**（原理实现；多条同序的环并行、各搬一份，第 0 节通道结构）——**归约阶段（= reduce_scatter，第 4 节的"边加边转发"轮次）**：各卡交换并合并对应元素，逐步累积部分和，阶段末**每卡只持有"和"的一段**：

    ```
    GPU0: (a0+…+a7)   GPU1: (b0+…+b7)   GPU2: (c0+…+c7)   GPU3: (d0+…+d7)
    GPU4: (e0+…+e7)   GPU5: (f0+…+f7)   GPU6: (g0+…+g7)   GPU7: (h0+…+h7)
    ```

    **分发阶段（= all_gather，第 3 节的"拼块"轮次）**：交换各自的段，每卡拼齐完整结果，此后 8 卡完全同步。
  - **NVLS（本机默认实际路径）**——NVLink SHARP：归约不在 GPU 上做，搬进 **NVSwitch 交换芯片内**完成（依赖 NVSwitch 的多播硬件，日志 `NVLS multicast support is available (NVLS_NCHANNELS 24)`；无 NVSwitch 的拓扑用不了）。两步机制：

    ```
    ① 上行归约:  8 卡全量 S ──NVLink──▶ NVSwitch（芯片内逐元素求和 8 份 → 1 份）
    ② 下行多播:  每 head ──S/8──▶ NVSwitch ──一份扇出──▶ 全部 8 卡
    ```

    **每步谁在计算、谁在搬运**：

    | 步骤 | 计算者 | 搬运者 | 搬运量/卡 |
    |---|---|---|---|
    | ① 上行归约 | **NVSwitch**（芯片内逐元素求和） | GPU → NVSwitch（NVLink） | +S |
    | ② 下行多播 | **无**（纯扇出） | head → NVSwitch → 8 卡（NVLink） | +S/8 |

    每 GPU 都是 head——各担任 1/8 结果的多播（日志 `headRank r`、`nvlsPerRankSize = 总量 1/8`）；每卡线上 = S + S/8 = **1.125×S**。三层后果：**字节**——比环形 1.75×S 省掉 0.625×S，省的正是"替别人转发"的部分；**计算**——求和发生在交换芯片内，**GPU 零求和**（对照环形：GPU 沿途加，每卡 (W−1)×C，第 4 节）；**结构**——不走环形/树形通道、走自己的多播结构（分析③实测：通道旋钮对它无效）。**执行方式**——不是"先归约、后分发"的两个先后阶段，而是**按块融合的流水线**：每块"上行 → 芯片内归约 → 多播写回"，块间重叠、上下行同时占线（链路全双工，每卡 Tx = S + S/8 同时计量）。
- **通信开销**：环形两阶段各 S×(W−1)/W（8 卡 = 7/8×S），合计 **2×S×(W−1)/W**（8 卡 = 1.75×S）——每步每卡只与环上**邻居**通信，多轮渐进的转发与合并让信息绕环一圈、无需中心协调者。NVLS 则降为 **1.125×S**（上行 S + 多播写回 S/8，见下面运行与分析）。

**形象介绍**：8 个人合写一份总账，最后**每人手里都要有一模一样的完整总账**。朴素做法（一人汇总再念给大家）有中心瓶颈；环形是"先分段算清（RS）、再互相拼齐（AG）"；NVLink 上 NCCL 默认还有第三种——**请账房先生（NVSwitch）代劳**：每人把自己那份交给账房，账房当场算好、一式八份念给所有人。

**PyTorch 代码**：`sn-codes/all_reduce.py`（单文件，三段式：① 小张量语义验证 → ② 16 GB × 5 次迭代计时 → ③ NVLink Tx 差值对账模型）。运行（Pod 内）：`cd /tmp/sn-codes && torchrun --nproc_per_node=8 all_reduce.py`。

**运行**（实测）：

```
=== all_reduce（全归约） ===
[语义] PASS: 每个 rank 均得到 [36,72,108,144]
[规模] 每 rank 输入 16 GB; 迭代 5 次
[耗时] 每次 33.265 ms | algbw 481 GB/s | busbw(环形口径) 842 GB/s
[流量] NVLink 实测: 每 GPU 平均 18.0064 GB/次 (min 18.0047 / max 18.0066)
[对账] 环形模型 28.0000 GB/次/GPU -> 实测/模型 = 0.643
```

**分析**：

**① 字节总量对账**：环形模型 1.75×S = 28.0000 GB/卡/次，实测 **18.0064 GB**（**0.643**）——七种操作中唯一显著低于模型的操作；+0.0064 GB ≈ 6 MB 协议开销。

**② 算法判定 = NVLS（分布 + 日志 + 分解三证据）**：
- **分布均匀**（18.0047–18.0066，偏差 <0.01%）排除树与 Ring 含死边（第 0 节指纹）；
- **日志独有 NVLS comm 行**（`NVLS comm ... headRank 0 nHeads 8 nvlsRanks 8`）——6 个操作中**只有 all_reduce 建立了 NVLS 通信资源**（其余只有能力行"NVLS multicast support is available"）；
- **字节分解精确吻合 NVLS 模型**：每卡 = S（上行给 NVSwitch 做归约）+ S/8（结果多播写回）= **1.125×S = 18.0 GB**，实测 18.0064 ✓；Ring 的 28 GB、树的 max 2×、无一吻合——**多播发一份、交换芯片扇出 8 份**，省掉的 0.875×S 正是"替别人转发"的部分。

**③ 并发结构：通道旋钮对 NVLS 无效（实测）**：强制 `NCCL_MAX_NCHANNELS` 1→32：

| 通道数 | 1 | 2 | 4 | 8 | 16 | 32（默认） |
|---|---|---|---|---|---|---|
| algbw (GB/s) | 481 | 480 | 481 | 481 | 480 | 481 |

  **完全平坦**——能把 Ring 类操作线性缩放的旋钮对 all_reduce 毫无作用：NVLS 不走环形/树形通道，走自己的多播结构（`NVLS_NCHANNELS 24`，日志）。这同时是 ② 判定的**独立反证**：若 all_reduce 是 Ring 实现，1 通道应塌到 ≈30 GB/s（对照 reduce 单通道 35 GB/s），实测 481。也说明 NVLS 的线速不受通道数约束——瓶颈在交换芯片归约路径本身。

**④ 性能**：33.265 ms——每卡线上实发 18.0 GB / 33.3 ms ≈ **541 GB/s**；busbw（环形口径 **842 GB/s**）反而**高于**实测线速——NVLS 下 busbw 是"环形等效"而非线速（第 0 节三层指标在此分离：环形若实现同样语义需每卡 28 GB，NVLS 实发 18 GB，等效比值 28/18 = 1.56 倍）。语义"最重"的操作（每卡要拿到完整结果）经 NVLS 后，实发字节（1.125×S）只比 AG/RS（0.875×S）多 29%。**NVLS vs 强制 Ring（16 GB 实测）**：33.3 对 40.2 ms（NVLS 快 17%）、每卡 18.0 对 28.0 GB（省 36%）——融合流水对张量级两阶段的净胜。

## 6. reduce_scatter + all_gather 组合（= all_reduce）

[↑ 返回目录](#目录)


**严格定义**：先 `out_r = (Σ_k x_k) 的第 r 段`，再对 {out_r} 做 all_gather——语义与字节都**恒等于 all_reduce**（环形 all-reduce 本身就是这两步拼成的）。

**原理走读（以 8 卡为例）**：

- **做什么**：输入同 reduce_scatter（每卡 8 段）→ 第一步后各持一段和（GPU_i 得第 i 段的总和）→ 第二步后**每卡**持有 `(A0+…+A7, B0+…+B7, …, H0+…+H7)`——与 all_reduce 的结果逐元素相同。
- **怎么做**：把 all_reduce（第 5 节）的两阶段拆开手写——先"分段算清"（RS，第 4 节）、再"人人拼齐"（AG，第 3 节）；两步各自多环并行。
- **通信开销**：RS (W−1)/W×总量 + AG (W−1)/W×总量 = **2×(W−1)/W×总量**（8 卡 = 1.75×总量），与环形 all_reduce 完全相同（本节实测 1.000）。

**形象介绍**：all-reduce 的"两步走"手工拆解版：先分段收账（每段的账算清在各家手里）、再拼图（家家拼回完整总账）。写成一个调用是 all_reduce，拆成两个调用就是 RS+AG。

**PyTorch 代码**：`sn-codes/rs_ag.py`（单文件，三段式：① 小张量语义验证 → ② 16 GB 级 × 5 次迭代计时 → ③ NVLink Tx 差值对账模型）。运行（Pod 内）：`cd /tmp/sn-codes && torchrun --nproc_per_node=8 rs_ag.py`。

**运行**（实测）：

```
=== reduce_scatter + all_gather（= all_reduce） ===
[语义] PASS: RS+AG 后每 rank 拼回全部段的和(= all_reduce 语义)
[规模] 输入 16 GB -> RS 出 2 GB -> AG 拼回 16 GB; 迭代 5 次
[耗时] 每次 45.949 ms | algbw 348 GB/s | busbw(环形口径) 609 GB/s
[流量] NVLink 实测: 每 GPU 平均 28.0017 GB/次 (min 28.0017 / max 28.0017)
[对账] 环形模型 28.0000 GB/次/GPU -> 实测/模型 = 1.000
```

**分析**：

**① 字节总量对账**：模型 2×7×C = 28.0000 GB/卡/次，实测 28.0017 GB（1.000）= RS(14.0009) + AG(14.0009) **精确相加**。

**② 算法判定 = Ring + Ring（分步可加性）**：均匀分布 28.0017 恰为第 3、4 节两步各自实测之和——两个调用各自默认 Ring（第 3、4 节判定）；无 NVLS comm 行：**即使语义等价 all_reduce，手写两步也拿不到 NVLS**——NVLS 是 all_reduce 单调用的整体优化，不作用于任意组合。

**③ 并发结构 = 32 通道（通道扫描实测）**：强制 `NCCL_MAX_NCHANNELS`：

| 通道数 | 1 | 2 | 4 | 8 | 16 | 32（默认） |
|---|---|---|---|---|---|---|
| algbw (GB/s) | 16 | 32 | 63 | 122 | 230 | **349** |

  每档位耗时 ≈ 两个组成操作之和（ch=1：1004.9 ms ≈ reduce 457.6 + AG 573.9；ch=32：45.9 ≈ 23.4 + 25.7）——组合在**任意通道数下都近似可加**，两步各走各的环形、互不搭车。

**④ 性能**：45.949 ms = RS(20.234) + AG(25.708)，误差 0.007 ms——**"AR = RS + AG" 的字节与时间双重等价实测成立**（第 0 节模型表的直接实证）。同一语义的三个价（16 GB 实测）：**NVLS 单调用 33.3 ms < Ring 单调用 40.2 ms（第 5 节④）< 手写两调用 45.9 ms**——手写比 Ring 单调用慢 14%（两个独立调用无跨阶段重叠，单调用在 RS→AG 边界有内部块间重叠）、比 NVLS 慢 38%（还丢了 NVLS）——**调用边界有价（+14%），算法选择更有价（再 +17%）**：这正是 NCCL 的价值——调用方式相同，库选到的路径不同。

## 7. all_to_all（全交换）

[↑ 返回目录](#目录)


**严格定义**：`out_r 的第 j 段 = x_j 的第 r 段`——每 rank 把输入等分（变长版不等分）成 W 段，**第 j 段只发给 rank j**；效果是 W×W 块矩阵的转置。

**原理走读（以 8 卡为例）**：

- **做什么**：对"GPU × 块"矩阵做转置（记号：`a_j` = GPU0 要发给 GPU j 的块，`b_j` = GPU1 的，依此类推；j = 0…7）：

  ```
  GPU0: (a0 a1 a2 a3 a4 a5 a6 a7)              GPU0: (a0 b0 c0 d0 e0 f0 g0 h0)
  GPU1: (b0 b1 b2 b3 b4 b5 b6 b7)              GPU1: (a1 b1 c1 d1 e1 f1 g1 h1)
     ...             all-to-all                   ...
     ...            ───────────►                  ...
  GPU7: (h0 h1 h2 h3 h4 h5 h6 h7)              GPU7: (a7 b7 c7 d7 e7 f7 g7 h7)
  ```

- **怎么做**：**点对点直达**——每卡同时开 W−1 条直达收发对，把第 j 块直接发给 GPU j，不经环转发、不替别人捎带（与 all_gather〔第 3 节〕的机制差异：AG"1 块绕圈 7 跳、人人经手全量"，a2a"7 对各一跳直达"；收发对同样按通道并行分组，第 0 节通道结构）：

  ```
  GPU0: ─a₁→GPU1  ─a₂→GPU2  …  ─a₇→GPU7     （同时发出 7 块，各 S/8）
        ─b₀←GPU1  ─c₀←GPU2  …  ─h₀←GPU7     （同时收回 7 块）
  ```

- **通信开销**：等分时每卡发出 7 × 块 = (W−1)/W × S，与 all_gather 字节相同——均衡负载下无优势，优势在稀疏/倾斜（只发"命中"的块）。

**形象介绍**：发扑克——每人手里 8 叠纸，第 j 叠只递给第 j 家；一圈下来，每人手里的第 j 叠恰好来自 j 家（手里的牌"转置"了）。与 all_gather 的本质区别：**只发"需要"的**，不是人手全量。

**PyTorch 代码**：`sn-codes/all_to_all.py`（单文件，三段式：① 小张量语义验证 → ② 16 GB × 5 次迭代计时 → ③ NVLink Tx 差值对账模型）。运行（Pod 内）：`cd /tmp/sn-codes && torchrun --nproc_per_node=8 all_to_all.py`。

**运行**（实测）：

```
=== all_to_all（全交换） ===
[语义] PASS: 转置语义: out 第 j 段 = rank j 的第 r 段
[规模] 每 rank 16 GB 等分发给 8 卡; 迭代 5 次
[耗时] 每次 20.960 ms | algbw 763 GB/s | busbw(环形口径) 668 GB/s
[流量] NVLink 实测: 每 GPU 平均 14.0017 GB/次 (min 14.0017 / max 14.0017)
[对账] 环形模型 14.0000 GB/次/GPU -> 实测/模型 = 1.000
```

**分析**：

**① 字节总量对账**：模型 0.875×S = 14.0000 GB/卡/次，实测 14.0017 GB（1.000）——与 all_gather 的 14.0009 **字节相同**：均衡负载下"每卡给 7 个同伴各发一份"与"AG 每卡经手 7 份"殊途同归。

**② 算法判定 = P2P 直达（排除法 + 机制）**：分布**完全均匀**排除 Ring 含死边、无 NVLS comm 行排除 NVLS（第 0 节指纹）；而环/树对 a2a **语义上不成立**——转置矩阵的每一块只有一个目的地，不存在"绕邻居逐跳传"的路径（环/树是聚合类操作的实现族，a2a 天然直达）。NCCL 的 a2a 实现即点对点直达（机制推断；字节与分布吻合）。环形口径的 0.875×S 在此只是**记账口径**（数值恰与直达相同），不是实现描述。

**③ 并发结构 = 32 通道（通道扫描实测）**：强制 `NCCL_MAX_NCHANNELS`：

| 通道数 | 1 | 2 | 4 | 8 | 16 | 32（默认） |
|---|---|---|---|---|---|---|
| algbw (GB/s) | 26 | 52 | 104 | 208 | 415 | **764** |

  每通道 ≈26 GB/s、1→16 通道**线性**——a2a 的"通道"是**收发对的并发分组**（非环的"图副本"），通道数缩放的是同时进行的直达对数；16→32 亚线性。通道只改并发度（共性见第 0 节）。

**④ 性能**：20.960 ms，每卡线速 ≈ **668 GB/s** = busbw；与 all_gather（25.708 ms）对比：**等分 a2a 反而更快**（763 对 622 GB/s algbw）——同样每卡发 14 GB，AG 的环要"逐跳中继 7 份"、a2a 是"7 份各一跳直达"（并行直达对串行中继）。

**⑤ 优势实测：稀疏路由（k 目标扫描，每 k 独立进程）**：变长 a2a（`all_to_all_single` 的 split_sizes，`sn-codes/a2a_sparse.py <k>`），每卡把 2 GB/块的数据只发往 k 个目标——MoE dispatch 的抽象（每块数据只需到达命中目标卡）：

| 目标数 k | 1 | 2 | 4 | 7（=等分外部） |
|---|---|---|---|---|
| 每卡实测 | **2.0002 GB** | 4.0005 | 8.0010 | 14.0017 |
| 模型 k×C | 2 | 4 | 8 | 14 |
| 比值 | **1.000** | **1.000** | **1.000** | **1.000** |
| 耗时/次 | 3.582 ms | 7.102 | 13.280 | 21.122 |

  **字节随目标数线性伸缩、逐点精确**——通信量 ∝ **有效流量**（目标数），而非 all_gather 的固定 7×C（人人全量）：k=1 时 a2a 只发 2 GB，为 AG 的 **1/7**——这就是稀疏路由（MoE）场景 a2a 对 AG 的碾压性优势的机制；k=7 点与等分实测（14.0017 GB）**逐位一致**，互为锚点。

  **方法学发现（实测）**：变长 a2a（含 0 块）在**同一进程内先跑过其他模式**（不同 k 的 a2a、甚至小张量检查）后，后续测量窗口携带**确定性超额流量**——k=1 实测可达 2.77 GB/卡（1.38×模型）、分布不均（金字塔形）、跨运行逐位可复现、**warmup 不吸收**（增至 20 次无效）、可持续 2 个以上窗口；机制未深挖（候选：分组点对点的计划/缓冲重配流量）。**协议：变长 a2a 每个模式用独立进程测首窗**——多次实验中全新进程首窗全部干净；等分（无 0 块）的 a2a 无此现象（14.0017 逐位稳定）。

## 9. NVLS 专题：概念、原理与应用

[↑ 返回目录](#目录)


<a id="s-9-1"></a>
### 9.1 概念

**NVLS（NVLink SHARP）**：把归约/多播从 GPU 搬进 **NVSwitch 交换芯片**内完成的技术——GPU 不互相转发、不在本地求和，交换芯片代劳（第 5 节实测的主角）。

- **谱系**（背景推断）：源自 InfiniBand 的 SHARP（Scalable Hierarchical Aggregation and Reduction Protocol，交换机内归约），NVLink 世代移植进 NVSwitch。
- **硬件前提**：NVSwitch 的多播（multimem）原语——一份写、交换芯片扇出多份。本机日志：`NVLS multicast support is available (NVLS_NCHANNELS 24)`；无 NVSwitch 的拓扑用不了。
- **资源**：启用时 NCCL 为通信器建立 NVLS comm——本机**仅 all_reduce 默认建立**（6 个操作中独有）；日志 `headRank r、nHeads 8、nvlsPerRankSize = 总量 1/8`（8 个头各管 1/8 结果）。

<a id="s-9-2"></a>
### 9.2 原理（一般模型，16 GB 实测归纳）

```
上行（归约类）: 各卡 ──全量上行──► NVSwitch（芯片内逐元素归约）
下行（分发类）: "头"卡 ──一份多播写──► 交换芯片扇出全部成员
```

**每步谁在计算、谁在搬运**（同 §5 表）：

| 步骤 | 计算者 | 搬运者 | 搬运量/卡 |
|---|---|---|---|
| ① 上行归约 | **NVSwitch**（芯片内求和） | GPU → NVSwitch（NVLink） | +S |
| ② 下行多播 | **无**（纯扇出） | head → NVSwitch → 8 卡（NVLink） | +S/8 |

**字节模型**（每卡）：

| 操作 | NVLS 实测 | 模型 | 对照环形 |
|---|---|---|---|
| all_reduce | 18.01 GB | **S + S/W**（上行归约 + 头多播） | 28.0 GB（省 36%） |
| all_gather | 2.04 GB | **≈C**（各卡只多播自己的块） | 14.0 GB（省 85%） |
| reduce_scatter | 16.04 GB | **≈S**（全量上行归约） | 14.0 GB（多 15%） |

三个一般性质（各节实测）：**计算**移入交换芯片（GPU 零求和，第 5 节）；**结构**独立于环/树通道（`NCCL_MAX_NCHANNELS` 无响应，第 5 节③）；**执行**为按块融合流水、无阶段边界（第 5 节）。

<a id="s-9-3"></a>
### 9.3 应用矩阵（16 GB 实测：默认 vs 强制）

| 操作 | 默认（算法/耗时） | 强制 Tree | 强制 NVLS | NVLS 字节/耗时 | 判定 |
|---|---|---|---|---|---|
| broadcast | Ring（含死边）/ 23.5 ms | ✗ 候选集无 Tree | ❌ 报错不支持 | — | 不适用 |
| reduce | Ring（含死边）/ 23.3 ms | ✗ 候选集无 Tree | ❌ 报错不支持 | — | 不适用 |
| all_reduce | **NVLS** / 33.3 ms | 49.3 ms（28.0 GB） | ✓ 33.3 ms | 18.0 GB | **净胜**：比 Ring 快 17%、省 36% |
| all_gather | Ring / 25.7 ms | ✗ 候选集无 Tree | ✓ 35.5 ms | 2.0 GB | 字节省 85% 但**慢 38%** |
| reduce_scatter | Ring / 20.2 ms | ✗ 候选集无 Tree | ✓ 23.9 ms | 16.0 GB | 字节多 15% 且**慢 18%** |

- **AR 分解自洽**：NVLS-AR(18.015) ≈ NVLS-RS(16.037) + NVLS-AG(2.041)，差 0.3%——"上行归约 + 多播写回"两段模型直接相加成立。
- **字节省 ≠ 时间省**：NVLS-AG 字节只有环形的 1/7 却慢 38%——交换芯片多播路径的吞吐低于 NVLink 环；NVLS-RS 字节反而多 15%（全量上行）。只有 AR（两段合并的语义）净胜——**这就是调优器只对 AR 默认启用的实测依据**。
- **算法候选集（源码 `tuning.cc:274-278`）**：broadcast/reduce → **只允许 Ring**；AG/RS → {PAT, Ring, NVLS, CollNet}（不含 Tree）；AR → {Ring, Tree, NVLS, CollNet}。Tree-AR 强制实测 49.3 ms、28.0 GB、分布 min 16 / max 32 GB（树指纹：近根发 2 份）——三种算法中最慢（NVLS 33.3 < Ring 40.2 < Tree 49.3 ms）。

<a id="s-9-4"></a>
### 9.4 边界与代价

- **硬件门槛**：需 NVSwitch 多播；无则 NVLS 不可用（NCCL 的回退行为未测）。
- **通道独立**：通道旋钮对 NVLS 无响应（第 5 节③）——NVLS 用自己的多播结构（`NVLS_NCHANNELS`）。
- **单调用整体优化**：语义等价的手写组合拿不到 NVLS（第 6 节：rs_ag 各走环形、比 NVLS 慢 38%）。
- **尺寸边界未测**：小消息下 NVLS 的固定开销（多播建立等）可能得不偿失——何时切换未在本文测（见未验证项）。

## 复现指南

[↑ 返回目录](#目录)


**最小复现**（第 1–7 节基准数据）：

1. 部署：`kubectl apply -f 8-gpu-8-fabric-pod.yaml`（单节点测试只需 pod-0；yaml 默认 `replicas: 4`，可降为 1）；
2. 拷入脚本：`kubectl cp sn-codes 8-gpu-8-fabric-pod-0:/tmp/ -c server`；
3. 逐操作运行：`kubectl exec 8-gpu-8-fabric-pod-0 -c server -- bash -c "cd /tmp/sn-codes && torchrun --nproc_per_node=8 <op>.py"`（broadcast/reduce/all_gather/reduce_scatter/all_reduce/rs_ag/all_to_all）；
4. 稀疏路由扫描（第 7 节⑤）：`for k in 1 2 4 7; do torchrun --nproc_per_node=8 a2a_sparse.py $k; done`——**每 k 必须独立进程**（§0.2 测量纪律）。

**扩展实验**：

- **通道扫描**（各节③ 数据源）：`kubectl exec -i 8-gpu-8-fabric-pod-0 -c server -- bash -s < scan_channels.sh`（6 操作 × 通道数 1/2/4/8/16/32）。
- **算法强制矩阵**（第 9.3 节数据源）：`for f in broadcast reduce all_reduce all_gather reduce_scatter; do NCCL_ALGO=NVLS torchrun --nproc_per_node=8 $f.py; done`（Tree 同法换 `NCCL_ALGO=Tree`；不支持组合会报错退出，即矩阵中的 ❌）。
- **算法/协议强制**：`NCCL_ALGO=Ring|Tree|NVLS`、`NCCL_PROTO=Simple|LL|LL128`；通道数：`NCCL_MAX_NCHANNELS=<n>`（Ring 类线性扩展，all_reduce 的 NVLS 对它无响应）。
- **证据抓取**：`NCCL_DEBUG=INFO`（grep `NVLS comm|Trees|Channel .* via`）；逐进程防交错用 `NCCL_DEBUG_FILE=/tmp/dbg/nccl.%p`（各节② 的 Trees/NVLS 日志即此法）。
- **单次核验**（疑点时用——分布异常、比值偏离模型）：`torchrun --nproc_per_node=8 nccl_bench.py --op <op> --mib <N> --iters 1` 独立重复数次，比对字节（应逐次一致）与耗时（孤立单次略慢于连发平均，broadcast 实测差 ≈7%）。

**注意**：

- 同节点同时刻只跑一个 NCCL 测量任务（§0.2）；Pod 重建后 `/tmp` 下脚本需重新 `kubectl cp`；NVLink 计数器为节点累计值，取差值即可、无需清零。
- 原始输出：`sn-results/sn-codes-16gb-20261017.txt`（全部实测数据）、`sn-results/sn-codes-20261017.txt`（过程记录）。
